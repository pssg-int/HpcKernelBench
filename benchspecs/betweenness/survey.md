# Survey: betweenness (singleton track)

Track has exactly 1 paper: `conf/ppopp/Shun20`, "Practical Parallel Hypergraph
Algorithms" (Julian Shun, PPoPP 2020). It is a suite paper covering 8
hypergraph algorithms (BC, MIS, k-core, hypertrees, hyperpaths, connected
components, PageRank, SSSP) built on an extended "Hygra" version of Ligra;
this track singles out its **hypergraph betweenness centrality (HyperBC)**
application.

## conf/ppopp/Shun20 — Practical Parallel Hypergraph Algorithms

**IMPORTANT artifact caveat** (see Divergences): the artifact the pipeline
attached to this paper, `github.com/DevSheth/prallel-hypergraph-algorithms`,
is a *third-party CUDA course-project reimplementation* of only 4 of the 8
algorithms (BFS, BPath, SSSP, PageRank) — it does **not** implement
betweenness centrality or MIS at all, and it is not the paper's own code.
The paper's actual, official artifact is the author's own repository
`github.com/jshun/ligra` (apps/hyper/ contains `HyperBC.C`, matching the
paper exactly), plus a dedicated artifact-evaluation companion repo
`github.com/jshun/ppopp20-ae` that ships the exact AE scripts, dataset
download links, and the machine/compiler config used to produce the paper's
numbers. This survey and the resulting spec are grounded in the **official**
`jshun/ligra` + `jshun/ppopp20-ae` sources, not the misattributed DevSheth repo.

- **Framework/algorithm**: `HyperBC` (apps/hyper/HyperBC.C in jshun/ligra) —
  a hypergraph generalization of Brandes' dependency-accumulation
  betweenness centrality, run from a single source vertex per invocation
  (same CLI convention as HyperBFS: `./HyperBC -s -r <source> <input>`,
  default source picked by the framework if `-r` omitted). This is a
  **single-source centrality computation**, not an all-pairs/exact BC over
  all vertices — the same scope as Ligra's classic (non-hypergraph) `BC` app.
- **Hardware** (from `jshun/ppopp20-ae/README.md`, "Getting Started Guide"):
  Dell PowerEdge R930, four 2.4GHz 18-core Intel Xeon E7-8867 v4 (72 cores,
  144 hardware threads via 2-way hyperthreading), 1TB RAM, Ubuntu 16.04,
  g++ 5.5.0 with Cilk Plus (OpenMP compilation also supported but Cilk Plus
  reported faster). `numactl -i all` used for all parallel runs.
- **Workloads/inputs** (from AE README "Datasets" section, exact download
  links given): real-world hypergraphs converted from SNAP/KONECT bipartite
  or community-membership graphs — `com-orkut` (SNAP com-Orkut community
  memberships), `friendster` (SNAP com-Friendster), `orkut-group` (KONECT
  orkut-groupmemberships), `web` (KONECT trackers-trackers), `livejournal`
  (KONECT livejournal-groupmemberships) — plus synthetic `rand1`/`rand2`/`rand3`
  random hypergraphs and a size-sweep family of random hypergraphs with
  10M vertices and 10M-100M hyperedges (cardinality 10 each, generated by
  the `randHypergraph` utility in `utils/`). Weighted variants exist for
  each (suffix `-wgh`) for the weighted algorithms (SSSP); BC uses the
  unweighted forms.
- **Timing protocol**: from `apps/hyper/HyperBFS -s <input>` example output
  in the AE README and from Ligra's general convention (confirmed in
  `jshun/ligra/README.md` for the non-hyper apps: "by default, the
  applications are run four times, with times reported for the last three
  runs... can be changed by passing `-rounds`"). The Hygra AE README states
  explicitly for hyper apps: **"by default, the programs are run for three
  trials... numbers reported in the paper take the minimum of three
  trials"** — i.e., paper reports **min-of-3**, not mean/median. MIS is the
  one exception in the suite, run only once because it mutates its input
  in place (not relevant to BC, but noted for the MIS track).
  Timer: internal wall-clock print (`Running time : <seconds>`), CPU-side,
  wraps only the algorithm call (graph is loaded once before any timed
  round).
- **Timing scope**: hypergraph load/parse time is excluded from "Running
  time" (loaded once before the timed rounds); no format-conversion cost
  is amortized into the per-round number because the same in-memory Hygra
  structure is reused across all 3 trials.
- **Precision & correctness**: BC produces a `double` dependency value per
  vertex (`fType = double` in HyperBC.C); no explicit correctness gate is
  visible in the AE scripts for BC specifically (the AE's `CheckAnswers`
  machinery is used for the LCA/bridge-style deterministic algorithms in
  the *other* singleton track, not this one) — this paper's own validation
  relies on algorithmic correctness proofs (work/depth bounds stated in the
  abstract), not an automated numeric check against ground truth.
- **Metric**: running time in seconds per algorithm/thread-count/dataset
  triple (Table 2 in the paper); parallel speedup vs. 1-thread baseline
  (`CILK_NWORKERS=1`) is the headline number (Figure 2), not a
  FLOPs/edges-per-second throughput metric — this suite reports **time and
  self-relative speedup**, not GTEPS.
- **Baselines**: (a) 1-thread run of the same Hygra code (parallel
  speedup baseline), (b) the MESH hypergraph processing system (external
  baseline, com-orkut only, via a separately downloadable MESH-format
  input), (c) for BFS/CC/SSSP only (not BC), the clique-expanded
  representation run through plain (non-hyper) Ligra — not applicable to BC
  since clique-expansion does not preserve betweenness centrality
  semantics.

Source: `jshun/ligra` (README.md, apps/hyper/HyperBC.C),
`jshun/ppopp20-ae` (README.md — hardware, dataset links, AE timing
conventions), abstract (`output/included.json`).

## Divergences

- **Artifact misattribution**: the pipeline's artifact-finder attached a
  third-party GPU course-project repo (DevSheth) that does not implement
  BC or MIS at all, rather than the paper's own repo. This spec is written
  against the paper's actual repos (`jshun/ligra`, `jshun/ppopp20-ae`)
  instead. Flagged so a future artifact-verification pass corrects the
  `artifact_url` field for `conf/ppopp/Shun20` in `included.json`.
- **min-of-3 vs. median/mean**: the paper's own AE documentation states it
  reports the **minimum** of 3 trials, not a central-tendency statistic.
  This is weaker than the bfs track's median+min/max convention (min-of-N
  is more susceptible to being a lucky outlier than median-of-N), but is
  disclosed explicitly rather than silently done, so this spec keeps the
  paper's own min-of-3 as the *headline* number while additionally
  requiring min/max/mean of the 3 trials to be reported (a strict superset
  of what the paper discloses, following the fairness principle "report
  min/max alongside").
- Since only one paper covers this track, there is no cross-paper
  divergence to resolve; the "Divergences" analysis here is between the
  paper's stated practice and this benchmark's stricter reporting
  requirement.
