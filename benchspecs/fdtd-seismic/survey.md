# FDTD-seismic track — evaluation-methodology survey

## Scope note (read this first)

Like `lattice-boltzmann`, no paper in the corpus carries the classifier slug
`fdtd-seismic` literally — `output/benchmark_groups.json` has no such key.
`benchmark_groups.py`'s own `DOMAIN` dict lists `fdtd-seismic` as an intended
sibling slug of `stencil`, but the classifier folded every FD-wave-equation
seismic paper into the generic `stencil`/`stencil_pde` bucket instead. This
track's paper list was built by filtering `output/included.json` for
seismic-context finite-difference **wave-equation** stencils specifically
(not any seismic-adjacent paper — see Exclusions below).

Of the 21 papers in the general `stencil` benchmark_groups.json group, exactly
**one** (`BisbasLLNGK21`) is both (a) genuinely FDTD-seismic and (b) has a
Phase-1-detected artifact — it is already the sole evidence source for
`stencil`'s own variant 3 (`stencil-e2e-application`). This survey reuses its
methodology facts from `benchspecs/stencil/survey.md` verbatim (same paper,
same source) and adds one directly-related follow-up paper found via this
survey's own manual search to have arXiv fulltext AND a shared artifact
lineage that Phase-1 missed (`BisbasNLLKG25`, arXiv 2312.13094 — its
distributed-memory-parallelism code is upstreamed into the same
`devitocodes/devito` repo, confirmed via `gh api search/code`). The remaining
2 papers (SaiMXA24, WangSWZGGWZFXY25) target proprietary dataflow/NPU hardware
(Cerebras wafer-scale engine, Huawei Ascend) with no public artifact found by
search — surveyed from abstract only.

**Exclusions** (seismic-adjacent papers found by keyword search but NOT
included as this track's papers, because they are not FD wave-equation
stencils):
- `conf/sc/LtaiefHWJRK23` ("Scaling the Memory Wall for Multi-Dimensional
  Seismic Processing... on Cerebras CS-2") — kernel is **tile low-rank
  matrix-vector multiply** (a dense-LA compression technique applied to
  seismic imaging's multi-dimensional-convolution operators), classified by
  the Phase-1 pipeline itself as `dense_la`, not `stencil_pde`. It has a
  real artifact (`github.com/ecrc/tlrmvm`) but belongs to a different kernel
  track (TLR matvec), not this one.
- `journals/tpds/HuYLGYQ20` ("Massively Scaling Seismic Processing on Sunway
  TaihuLight") — kernels are **Common Midpoint (CMP)** and **Common
  Reflection Surface (CRS)**, post-stack seismic *data processing* /
  traveltime-analysis techniques, not forward FD wave-equation modeling. No
  artifact found either way.

## Bisbas et al. — temporal blocking of FD stencils with sparse off-the-grid sources
IPDPS 2021, `conf/ipps/BisbasLLNGK21`, arXiv 2010.10248, Devito artifact.
**Reused verbatim from `benchspecs/stencil/survey.md`** (same paper, same
source — see that file for the full entry); summarized here for this track's
seismic-specific axes:

- **Workloads**: isotropic acoustic (space order 4/8/12), anisotropic/TTI
  acoustic (rotated-Laplacian, space order 4/8/12), isotropic elastic
  (1st-order-in-time, space order 4/8/12) — all 3D FD wave-propagation
  operators generated by the Devito DSL, single-node (not distributed).
- **Grid**: 512^3, spacing 10m (isotropic/elastic) or 20m (TTI).
- **Order of accuracy**: space order swept at {4, 8, 12} — a first-class axis
  of the paper's own results, not fixed at one value.
- **Absorbing boundaries**: not itself the paper's contribution (temporal
  blocking is), but Devito's standard damping-layer ABC is implicit in the
  velocity-model setup; not quantified as a separate cost in the extracted
  text.
- **Timesteps**: CFL-determined — 228 (isotropic acoustic), 436 (elastic),
  587 (TTI), all covering 512ms of simulated time (NOT an arbitrary round
  number).
- **Metric**: GPoints/s, plus roofline analysis.
- **Baseline**: Devito's own spatially-blocked-only code (temporal-blocking
  on/off ablation within the same compiler, same generated code otherwise).
- **Source**: ar5iv.labs.arxiv.org/html/2010.10248 (already fetched for
  `stencil` track).

## Bisbas et al. — Automated MPI-X Code Generation for Scalable FD Solvers
IPDPS 2025, `conf/ipps/BisbasNLLKG25`, arXiv 2312.13094 (arxiv.org/html
fulltext), **artifact upstreamed into `devitocodes/devito`** (`gh api
search/code?q=repo:devitocodes/devito+diag2` confirms `diag2`/`basic`/`full`
MPI halo-exchange modes and `benchmarks/user/benchmark.py` live in the main
repo — Phase-1 recorded `artifact_status: none` for this specific paper key,
which this survey corrects by tracing the contribution to its parent
project's repo)

- **Workloads**: 4 wave propagator kernels — isotropic acoustic (star
  stencil, Laplacian, 5 fields, memory-bound), anisotropic/TTI acoustic
  (coupled 2-PDE system, rotated Laplacian, 12 fields, arithmetically
  intensive), isotropic elastic (1st-order-in-time, 9 wavefield parameters,
  22 grids, highly memory-bound), visco-elastic (1st-order-in-time, 15
  stencil updates, 36 grids).
- **Grid sizes**: 1024^3 (acoustic/elastic/TTI), 768^3 (visco-elastic);
  **with absorbing boundary conditions: 1120^3 total domain including a
  40-point-deep ABC layer** — i.e. the ABC's memory/compute footprint is
  directly quantified as +96 points per dimension (1120 vs 1024), not
  hand-waved. Weak-scaling runs use a smaller 256^3 per-node base size,
  cyclically doubled with node count.
- **Order of accuracy**: space discretization order (SDO) swept at
  {4, 8, 12, 16} — primary results at SDO 8 and 12, SDO 4/16 in appendices.
  This is the single most direct source in this whole survey for the
  "order of accuracy" axis this track's parent task explicitly calls out.
- **Timesteps**: acoustic/TTI 290 steps (512ms simulated), elastic 363
  steps, visco-elastic 251 steps — again CFL/physics-determined, not
  arbitrary.
- **Hardware**: ARCHER2 (dual AMD EPYC 7742 Rome, 128 cores/node), HPE
  Slingshot/dragonfly interconnect, scaling demonstrated up to 128 nodes
  (16,384 cores); 8 MPI ranks/node x 16 OpenMP threads/rank.
- **Metric**: throughput in Gpts/s (Giga-points/s) for every benchmark —
  this is this track's primary metric's exact literal source.
- **Baselines/axes**: 3 distinct MPI halo-exchange communication patterns
  compared head-to-head — `basic` (synchronous multi-phase), `diag2`
  (synchronous single-phase with diagonal exchanges), `full` (asynchronous
  compute/communication overlap) — this is a genuine, paper-native axis for
  a distributed-scaling variant, not an invented one.
- **Timing/statistic**: single-node performance separately "optimised and
  tuned through flop-reduction transformations and loop blocking
  autotuning" before the distributed numbers are reported; explicit
  warmup-repetition/statistic convention not stated in the extracted
  fulltext (same gap as `stencil` survey's BisbasLLNGK21 entry — the Bisbas
  papers consistently omit this detail from their public text even when
  fulltext is available).
- **Compiler/precision**: Cray Clang (Cray Compiler Environment) 11.0.4;
  precision not explicitly stated in the extracted text, geophysics
  convention implies fp64 (open question, not confirmed).
- **Source**: arxiv.org/html/2312.13094v1 (Evaluation section, fetched
  directly); `github.com/devitocodes/devito` — `benchmarks/user/README.md`
  (`benchmark.py --shape`, `--space-order`, `--tn` CLI flags confirmed via
  `gh api`), `devito/mpi/routines.py`.

## Sai, Mellor-Crummey, Xu & Araya-Polo — high-order stencils for a dataflow architecture
SC 2024, `conf/sc/SaiMXA24`, no OA/arXiv fulltext found; **abstract only**;
no public artifact found (target hardware is Cerebras' wafer-scale engine, a
closed proprietary dataflow accelerator — code targeting it is
characteristically not releasable independent of vendor SDK access)

- **Workload framing**: "finite-difference methods based on high-order
  stencils... widely used in seismic simulations, weather forecasting, and
  computational fluid dynamics" — explicitly names seismic as one of 3
  target application domains, not the sole focus (weather/CFD are the other
  2, which is itself informative for this track's overlap with
  `climate-kernel`).
- **Contribution**: automated code generation addressing dataflow-specific
  challenges — "managing the routing of data communications" and
  "accommodating a significantly constrained memory footprint" (wafer-scale
  engines have no DRAM in the conventional sense; working set must fit
  on-chip).
- **What could not be confirmed from the abstract alone**: specific stencil
  orders, grid sizes, timestep counts, precision, timing protocol,
  correctness method, or a Gpts/s-comparable metric.
- **Source**: abstract from `output/included.json` only.

## Wang et al. — Accelerating Half-Precision Seismic Simulation on NPU
TPDS 2025, `journals/tpds/WangSWZGGWZFXY25`, no OA/arXiv link recorded;
**abstract only**; no public artifact found (target hardware is Huawei
Ascend NPU, a proprietary accelerator ecosystem)

- **Workload**: CGFDM (Curvilinear-Grid Finite-Difference Method) — a 3D FD
  seismic-simulation solver specifically chosen for its ability to handle
  irregular regions of interest via a curvilinear (non-Cartesian) mesh; used
  for earthquake-hazard evaluation and earthquake-physics understanding.
- **Precision**: half-precision (FP16) storage + mixed-precision arithmetic,
  explicitly the paper's contribution — "increases data throughput and
  computing efficiency" via an NPU matrix-unit-enabled 3D difference
  algorithm exploiting both the matrix unit and wide SIMD lanes.
- **Headline result** (from web search snippet, not fulltext-verified):
  4.19x speedup vs. a parallel CGFDM solver on two AMD CPUs; validated on a
  real-world case (2008 Wenchuan earthquake simulation) — i.e. this paper
  has a genuine physical-validation correctness story (matching a real
  seismic event), not just a synthetic-grid speed number, though the exact
  agreement metric was not confirmed from the abstract alone.
- **What could not be confirmed from the abstract alone**: grid size,
  curvilinear mesh resolution, timestep count, order of accuracy, timing
  protocol/repetitions, exact precision-drop tolerance vs. the fp64/fp32
  baseline.
- **Source**: abstract from `output/included.json`, plus one unverified
  web-search snippet for the 4.19x headline number (flagged, not asserted
  as fulltext-confirmed).

## Divergences

1. **Order-of-accuracy sweeps are a first-class, paper-native axis in this
   track, unlike the general `stencil` track.** Both Bisbas papers
   explicitly sweep space discretization order (4/8/12 in BisbasLLNGK21;
   4/8/12/16 in BisbasNLLKG25) as a primary reported dimension, not a fixed
   implementation detail. This is the direct evidentiary basis for making
   order-of-accuracy an explicit spec input rather than folding it into
   "grid_sizes" the way the general `stencil` spec does.

2. **Absorbing-boundary cost is quantified in exactly one paper
   (BisbasNLLKG25: +96 points/dimension for a 40-point ABC layer, 1024^3 ->
   1120^3) and entirely unaddressed in every other paper surveyed here.**
   This is a genuine gap: the general `stencil` track's variant 1 explicitly
   EXCLUDES boundary/halo handling from the timed kernel-only region, but
   FDTD-seismic's absorbing boundary is not a communication halo — it's
   physically extra, damped grid volume that IS part of the compute, and
   skipping it (as most surveyed papers implicitly do by not mentioning it)
   understates real cost. The spec makes ABC width a mandatory, explicit
   input rather than an afterthought.

3. **Distributed-scaling communication-pattern choice (basic/diag2/full) is
   a genuine, paper-native axis (BisbasNLLKG25) with no analogue in the
   general `stencil` track's papers** (none of which are distributed-memory
   MPI codes at the scale BisbasNLLKG25 demonstrates — up to 16,384 cores).
   This motivates a dedicated distributed-e2e variant rather than trying to
   force this track's numbers into `stencil`'s single-node-only variant 1/2
   structure.

4. **Proprietary-hardware papers (Cerebras, Ascend NPU) cannot be
   code-verified by construction**, unlike the general `stencil` track's
   AN5D/PERKS/ConvStencil which target commodity NVIDIA GPUs with public
   CUDA toolchains. This is a structural, not incidental, gap — variant 3
   below is explicitly the lowest-confidence variant in this track's spec
   and is flagged as such throughout.

5. **This track shares its two code-grounded papers' underlying artifact
   (`devitocodes/devito`) with the general `stencil` track's variant 3**
   (which already uses BisbasLLNGK21 as its sole evidence source). This
   spec's variant 1 is therefore intentionally near-identical to `stencil`'s
   variant 3 in its single-node facts, but reframed around this track's own
   seismic-specific primary axes (order of accuracy, ABC cost, GPoints/s as
   THE primary metric rather than one of several) rather than duplicating
   `stencil`'s framing verbatim.
