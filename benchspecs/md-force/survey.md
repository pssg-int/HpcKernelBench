# md-force — evaluation-methodology survey

`data/track_inputs/md-force.json` does not exist. `output/benchmark_groups.json`
lists exactly **one** artifact-bearing paper under the `md-force` slug (the
canonical-slug normalization pass in `data/normed/` only ran on the 310
artifact-bearing papers, and only one of those was tagged `md-force`). The
full 917-paper `output/included.json` corpus, however, contains **18** papers
whose raw `kernels` field is clearly MD-force-related (Lennard-Jones, EAM,
Tersoff, ReaxFF, AIREBO, ILP, MLIP force kernels, neighbor-list build,
Ewald/PME) but that were normalized before the artifact-scoped slugging step
ran, or lack an open-source artifact. Per task instructions this survey
broadens beyond the single `benchmark_groups.json` entry to that recovered
18-paper pool so that the ≥2 (and preferably ≥5) paper requirement is met with
real evaluation methodology, not placeholders. 6 papers were surveyed, 5 via
arXiv fulltext / artifact repo, 1 via abstract only.

## Surveyed papers

### 1. LMFF — layered-materials force field on Sunway (SC'21)
`conf/sc/0005DGWSCMLZMLC21`, DOI 10.1145/3458817.3476137. Source: artifact
repo `github.com/run-towards-the-future/LAMMPS-LMFF`, `README.md` (AD/AE
appendix), read via `gh api`.

- **Workload**: built on stock LAMMPS `3Mar2020`; Tersoff + inter-layer
  potential (ILP) for layered materials (graphene, hexagonal boron nitride).
  Two named cases: `case_5016` (6-layer graphene, 5,016 atoms, 1 core group /
  1 process) and `case_1672w` (double-layer graphene, 16,720,000 atoms, 1,536
  processes / 256 nodes). Weak/strong scaling generated by `-var SX <n>`
  (replicate system n× in x).
- **Timing protocol**: energy minimization first (not timed), then a 200-step
  run split into **four separate 50-step simulations**, each separately
  timed; thermo output every 10 steps; README recommends **≥5 repeated
  experiments**, averaging the four per-experiment values as one observation.
- **Timing scope**: LAMMPS's own MPI phase timer (pair/neigh/comm/output
  split) PLUS the General Purpose Timing Library (GPTL) instrumented into the
  optimized kernels for fine-grained profiling — this is the one paper in the
  pool that explicitly separates neighbor-list time from force-kernel time.
- **Metric**: **timesteps/s explicitly preferred over ns/day and hours/ns**
  — the README states ts/s "is more accurate than the other two" (a direct,
  citable fairness argument from within the track's own literature).
- **Precision / correctness**: fp64 (LAMMPS default); no explicit
  energy-drift or force-vs-reference correctness check documented beyond
  LAMMPS's standard thermo output.
- **Results**: baseline LMFF ≈0.48 ts/s (0.042 ns/day) at 5,016 atoms/1
  process; optimized SWLMFF ≈11.5 ts/s (1 ns/day) at the same size (~24×).
  At 16.72M atoms/256 nodes: LMFF ≈0.7 ts/s vs SWLMFF ≈15 ts/s (~21×). Weak
  scaling efficiency 95–100% up to 2.7M atoms/process; largest system ≈2^31
  atoms.

### 2. Jia et al. — GPU DeePMD-kit, 100M atoms (SC'20 Gordon Bell winner)
`conf/sc/JiaWCL0CEZ20`, DOI 10.1109/SC41405.2020.00009, arXiv:2005.00223
(fulltext via `ar5iv.labs.arxiv.org/html/2005.00223`).

- **Workload**: two systems — **water** (12.8M–679.5M atoms) and **copper**
  (8M–127.4M atoms); single-GPU correctness check on a 12,288-atom (4,096
  H2O molecule) box.
- **Cutoff / neighbor list**: water cutoff 6 Å (144 neighbors/atom); copper
  cutoff 8 Å (512 neighbors/atom); **2 Å skin buffer, list rebuilt every 50
  steps** for both.
  System scale.
- **Timing protocol**: core numbers from a 500-step MD loop (force+energy
  evaluated 501×); an extended 5,000-step (5 ps) run on the 127M-atom Cu
  system checks long-run stability. Reported time is **the full MD loop
  including I/O**, excluding one-time setup — an explicit, if generous,
  timing-scope choice.
- **Metric**: PFLOPS (double / mixed-32 / mixed-16) and derived ns/day.
- **Precision**: three configurations — fp64, MIX-32 (32-bit
  storage+compute), MIX-16 (half precision in the embedding net).
- **Correctness**: mixed-precision force/energy error vs the fp64 run
  (MIX-32: energy err 5.2e-6 eV, force RMSD 2.5e-6 eV/Å; MIX-16: energy err
  3.6e-3 eV, force RMSD 5.7e-3 eV/Å); radial distribution function (RDF)
  cross-checked against ab initio MD (AIMD) reference, reported to "agree
  perfectly".
- **Results (4,560 Summit nodes, 127M-atom Cu)**: fp64 91 PFLOPS (45.5% of
  peak) → 8.1 ns/day; MIX-32 162 PFLOPS → 14.6 ns/day; MIX-16 275 PFLOPS →
  24.9 ns/day. Baseline: original 2018 DeePMD-kit on a 25K-atom single-GPU
  system at 5.6e-5 s/step (>1000× slower, but note this baseline comparison
  changes system size AND hardware simultaneously).

### 3. TensorMD — tensor-diagram MLIP on Sunway (arXiv 2023, SC'25)
`conf/sc/OuyangC00SCL0WL25`, DOI 10.1145/3712285.3759844, arXiv:2310.08439
(fulltext via `arxiv.org/html/2310.08439`, extended to SC'25; SC version DOI
differs but the methodology is the same lineage).

- **Workload**: single material — **tungsten (W)**. Intel-node correctness/
  micro-benchmarks at 128 / 6,912 / 55,296 atoms; Sunway per-process sizes
  85,750 (tensor rank k=32) / 23,040 (k=128) atoms; full-machine run up to
  **52.6 billion atoms**.
- **Cutoff / neighbor list**: binning-method neighbor list, **1 Å skin
  buffer, rebuilt every 5 steps** (an order of magnitude more frequent than
  the DeePMD papers' 50-step convention). Cutoff radius value itself not
  stated in the accessible text.
- **Timing protocol**: 50-step runs for scalability figures; 1 fs timestep,
  NVT @300 K; thermo recorded every 10 steps; loop time per step; **no
  explicit warmup phase documented**.
- **Metric**: **s/step/atom (atom-normalized time)**, not a throughput rate
  — reported as 3.1e-11 s/step/atom at 52B atoms; single-node comparisons use
  μs·core/step/atom.
- **Precision**: fp64 throughout (no mixed-precision variant explored, unlike
  the DeePMD papers).
- **Correctness**: static force RMSE vs. the non-interpolated (direct
  network-evaluation) reference; potential accuracy vs DFT — energy MAE 4.1
  meV/atom, force MAE 0.08 eV/Å, stress MAE 0.51 GPa; dynamic check compares
  total-energy/temperature/pressure trajectories.
- **Baselines**: other MLIPs on the same W system, all in μs·core/step/atom
  (lower=faster) — DP-SE2 657, DP-HYB 1,475, GAP-2 4,585, classical MEAM
  14–16 (for scale reference), TensorMD itself 34–282 depending on config.
  At extreme scale: SNAP (20B C atoms, Summit, the 2020 Gordon-Bell winner)
  3.5e-11 s/step/atom, DP (17B Cu, Fugaku) 4.1e-11 vs TensorMD 3.1e-11 (52B
  atoms) — basis of the paper's "1.88× over SOTA MLIP" A100 claim.

### 4. Cerebras Wafer-Scale Engine EAM (SC'24)
`conf/sc/SantosMOSSTKPSP24`, DOI 10.1109/SC41406.2024.00014, arXiv:2405.07898
(fulltext via `arxiv.org/html/2405.07898`).

- **Workload**: **classical EAM potential**, three metals — Cu, W, Ta.
  Primary benchmark: 801,792-atom bulk crystal (thin-slab geometry, ~60nm ×
  60nm × 2nm, open boundaries) per material; weak-scaling sweep from ~1k to
  800k atoms; a grain-boundary case at 61,600 atoms / 62,500 cores. Systems
  pre-equilibrated in **LAMMPS for 20k timesteps at 2 fs/step** before
  porting to the WSE.
- **Neighbor handling — fundamentally different cost model**: the WSE has no
  amortized Verlet/cell list at all. Every timestep, each PE does a
  "candidate exchange" (multicast atom positions to a (2b+1)² neighborhood)
  then filters on-chip via r_ij² < r_cut² (no sqrt). There is no
  "rebuild frequency" concept — the full neighbor search cost is paid every
  step, which is only tractable because it's mapped to dedicated systolic
  hardware.
- **Timing protocol**: 8,000-timestep runs, timed via a hardware clock-cycle
  counter recorded in scratch memory; cross-validated for stability over
  million-timestep intervals. Timestep 2 fs.
- **Metric**: **timesteps/second** (matches LMFF's stated preference).
- **Results (800k atoms)**: Ta 274,016 ts/s vs Frontier LAMMPS/HIP-Kokkos-EAM
  1,530 ts/s (179×) vs Quartz CPU 4,938 ts/s (55×); W 96,140 ts/s (96×/26×);
  Cu 106,313 ts/s (109×/34×).
- **Precision — a fairness flag**: **WSE runs fp32; the LAMMPS/Frontier and
  Quartz baselines run fp64.** The reported 179×/96×/109× speedups therefore
  conflate a hardware change, an architecture-paradigm change (dataflow vs.
  von Neumann), AND a precision downgrade, all at once. No explicit
  energy-conservation or force-accuracy check is reported for the WSE
  fp32 run in the accessible text.

### 5. DeePMD-kit at 149 ns/day on Fugaku (SC'24)
`conf/sc/LiLGLLLYWTJ24`, DOI 10.1109/SC41406.2024.00036, arXiv:2410.22867
(fulltext via `arxiv.org/html/2410.22867v1`).

- **Workload**: **copper** (0.54M atoms) and **water/H2O** (0.56M atoms,
  558K molecules) — same DeePMD-kit lineage as paper 2, same force-field
  class, different hardware (A64FX/Fugaku vs. Summit GPUs).
- **Cutoff / neighbor list**: Cu cutoff 8 Å, water cutoff 6 Å (identical to
  paper 2 — same reference DeePMD conventions), **2 Å skin, rebuilt every 50
  steps**.
- **Timing protocol**: **100 measured steps + an explicit 10-step warmup** on
  a 96-node calibration run; full results scaled from 768 to 12,000 nodes.
  Timestep 1.0 fs (Cu), 0.5 fs (water) — **different physical timestep per
  system**, which matters because...
- **Metric**: **ns/day** (the metric LMFF explicitly argues against) —
  reported as wall-clock-normalized simulated time, so the Cu (1.0 fs/step)
  and water (0.5 fs/step) numbers are NOT directly comparable step-for-step
  despite sharing a unit.
- **Precision**: fp64 baseline; MIX-fp32 (embedding+fitting net); MIX-fp16
  (fitting-net GEMM only, i.e. `sve-gemm`).
- **Correctness**: MIX-fp16 energy error 4.0e-3 eV/atom, force error 4.4e-2
  eV/Å vs fp64; RDF vs ab initio reference reported to overlap "perfectly".
- **Results**: Cu 149 ns/day @12,000 nodes (31.7× vs. the original
  DeePMD-kit's 4.7 ns/day) — **but the baseline ran a different problem**
  (2.1M Cu atoms / 218.8K cores) than the optimized run (0.54M atoms / 576K
  cores); atoms-per-core differs by >8×, so the 31.7× figure is not a
  fixed-problem speedup. Water: 68.5 ns/day (32.6×). Parallel efficiency
  62.3% (Cu) / 57.9% (water) at 12,000 nodes.

### 6. ReaxFF billion-atom simulation on Sunway (TPDS'20) — abstract only
`journals/tpds/GaoDZZSZSZGXFLY20`, DOI 10.1109/TPDS.2020.3008499. No arXiv
preprint found; IEEE Xplore/TPDS fulltext paywalled. Source: abstract +
secondary summaries (Semantic Scholar / dblp / ResearchGate listings).

- **Workload**: **ReaxFF reactive force field** with charge equilibration
  (QEq) solved via pipelined conjugate gradient — the one classical-potential
  paper in the pool that couples the force kernel to an iterative linear
  solve every step, distinct from LJ/EAM/Tersoff/ILP's purely local force
  evaluation.
- **Contribution** (from abstract): redesigned force-analysis and
  **neighbor-list-building** steps; isolated-computation-and-update strategy
  for many-body terms; inverse-trig optimizations.
- **Scale claim**: 1,358,954,496 atoms on 4,259,840 cores at **0.015 ns/day**
  — described as "the first realization of chemical reaction simulation with
  a millimeter-scale force field."
- **Not recoverable from the abstract**: warmup/repetition count, timer,
  precision, correctness/energy-conservation validation. Left as an open
  question below.

## Divergences

- **No common reference suite.** None of the 6 surveyed papers — nor, as far
  as titles/abstracts of the other 12 candidates indicate, any paper in the
  18-paper pool — uses the canonical LAMMPS `bench/` suite (`in.lj`, `in.eam`,
  `in.rhodo`) that the wider MD-HPC community treats as the closest thing to
  a standard. Every paper instead sizes a bespoke production system (graphene
  slabs, bulk-metal crystals, water boxes, hydrocarbon ReaxFF systems) to its
  target machine's core count. This is itself the track's biggest fairness
  problem: cross-paper numbers are not just differently reported, they were
  never run on comparable inputs to begin with.
- **Metric units disagree, and not just cosmetically.** timesteps/s (LMFF,
  Cerebras WSE — both explicitly reasoned choices) vs. ns/day (DeePMD ×2,
  ReaxFF Sunway) vs. PFLOPS (Jia et al.) vs. s/step/atom (TensorMD, the only
  atom-normalized metric in the pool). ns/day is the most dangerous of these:
  it silently absorbs the physical integration timestep (0.5 fs water vs.
  1.0 fs Cu vs. 2 fs EAM/Ta), so two "ns/day" numbers from different systems
  are not doing the same amount of numerical work per reported unit.
  **atom-steps/s = atoms × timesteps/s is the only metric in the pool that is
  simultaneously throughput-comparable across system size (unlike PFLOPS,
  which needs a FLOP-counting convention per force field) and insensitive to
  the physical-timestep choice (unlike ns/day).**
- **Neighbor-list rebuild frequency is a real, reported design choice, not
  an afterthought**: every-50-steps (both DeePMD papers, same code lineage),
  every-5-steps (TensorMD), effectively every-step with no amortization at
  all (Cerebras WSE's dataflow architecture — a structurally different cost
  model that a rebuild-frequency field can't even express). Skin buffer also
  differs (2 Å vs 1 Å) between papers using the same 50-vs-5-step choice.
- **Force-field compute class differs by orders of magnitude.** Classical
  pairwise/many-body potentials (LJ, EAM, Tersoff, ILP, ReaxFF) do O(1)
  flops per neighbor with small per-atom working sets; MLIP force fields
  (DeePMD, TensorMD) evaluate a neural network (embedding net + fitting net,
  often GEMM-dominated) per atom and are 100–1000× more compute-intensive per
  atom-step. A single kernel-only variant cannot fairly compare a Tersoff
  paper's atom-steps/s against a DeePMD paper's — the spec splits these into
  separate variants.
- **Precision baselines are frequently confounded with hardware/problem-size
  changes.** Only the two DeePMD papers report same-hardware,
  same-problem-size precision ablations (fp64 vs MIX-32 vs MIX-16) with
  quantified error. Cerebras WSE reports fp32-vs-baseline-fp64 across
  DIFFERENT hardware; the Fugaku DeePMD paper's headline 31.7× conflates an
  8×+ change in atoms-per-core with the precision/optimization changes. The
  spec below keeps the fp64-baseline-with-reported-precision-variant pattern
  from the DeePMD papers (the pool's best practice) and treats
  cross-hardware "speedup" claims as out of scope for the benchmark itself.
- **Timing-scope and repetition practice vary widely.** LMFF is the most
  rigorous (≥5 repeated experiments, explicit phase-level GPTL breakdown
  including neighbor-list time). Jia et al. include I/O in the timed loop
  and use a single 500-step run. The Fugaku DeePMD paper is the only one with
  an explicit warmup count (10 steps) before the measured window (100 steps).
  TensorMD and Cerebras WSE report single-run point numbers (WSE substitutes
  long-run stability checks for repetition). None report a statistic
  (median/mean/min) explicitly — all appear to report a single observed
  rate per configuration.

## Open questions

- Exact cutoff radii for LMFF's Tersoff/ILP potentials and for the Cerebras
  WSE's Cu/W/Ta EAM potentials were not recoverable from the accessible
  sources (repo README and arXiv abstract-page extraction respectively);
  the spec falls back to LAMMPS `bench/` defaults where a paper doesn't
  state its own value.
- No paper in the surveyed set reports a quantitative NVE energy-drift
  tolerance (the textbook MD correctness check) — all instead validate via
  RDF-match-to-AIMD or force-RMSE-vs-reference-network. The spec's
  correctness gate for the classical-potential variant therefore borrows the
  energy-drift convention from the broader LAMMPS/MD literature rather than
  from this pool.
- `conf/sc/ToutouniCTH26` (OCTANE, ICS'26 Best Paper, "Breaking the
  Neighbor-List Bottleneck in GPU Molecular Dynamics") is exactly on-topic
  for the neighbor-list-build axis but its ACM DL / IEEE Xplore pages 403'd
  and no arXiv preprint was found; worth a follow-up pass once/if a preprint
  appears.
- `journals/tpds/GaoDZZSZSZGXFLY20` (ReaxFF billion-atom Sunway) — full
  timing protocol, precision, and correctness methodology unrecovered
  (paywalled, no preprint); only the scale/metric claim from the abstract
  is usable.
- `journals/tpds/ChenASGDSYCGYL26` (LJ + Tersoff on ARM Kunpeng, TPDS'26) is
  the pool's one paper explicitly using the textbook LJ/Tersoff LAMMPS
  potentials rather than a bespoke production system, which would have been
  a strong 7th data point for the "standard benchmark" axis — IEEE Xplore
  fulltext paywalled, abstract only reachable via search snippets, not
  surveyed in full.
