# SpTRSV track — evaluation methodology survey

Track input: `data/track_inputs/sptrsv.json`, 5 papers (all 5 surveyed — the
full track). None of the 5 have an arXiv id in the track file, so all 5 were
surveyed **via code-verified artifact repos** (`gh api`), which for SpTRSV
turns out to be strictly more reliable than the papers' text anyway: the
timing-loop code reveals a methodological detail (how the "triangular factor"
input is actually produced) that none of the abstracts mention at all. One
paper's PDF (the SC'23 paper, no public repo-hosted paper copy) was fetched
directly and text-extracted with `pypdf` for its Experimental section and
Artifact-Description appendix.

Operation surveyed throughout: solve `L*x = b` (or `U*x=y` for the back-solve
half) for `x`, `L` sparse lower-triangular `n x n`, `b`/`x` dense, almost
always **single right-hand side** (nrhs=1) in the benchmark code paths, even
where the surrounding paper/library nominally supports multiple RHS.

---

## 1. Liu, Ding, Sao, Williams, Li — Unified Communication Optimization
   Strategies for SpTRSV on CPU and GPU Clusters (SC'23)

- key: `conf/sc/01790S0L23`, artifact: github.com/xiaoyeli/superlu_dist
  (feature branch `gpu_trisolve_new`; upstream default-branch repo is the
  general-purpose SuperLU_DIST library, not a standalone paper artifact —
  the 3D SpTRSV code is one algorithm path inside a much larger distributed
  sparse-direct-solver codebase, selected via `NEW3DSOLVE`/
  `NEW3DSOLVETREECOMM`/`SUPERLU_ACC_SOLVE` env vars).
- **workloads** (paper Table 1, text-extracted): 6 matrices — `nlpkkt80`
  (n=1,062,400, nnz(LU)=1.93B, optimization), `Ga19As19H42` (n=133,123,
  nnz(LU)=1.57B, chemistry), `s1_mat_0_253872` (n=253,872, nnz(LU)=425M,
  fusion, **not** in SuiteSparse), `s2D9pt2048` (n=4,194,304, nnz(LU)=811M,
  synthetic 2D 9-point Poisson, **not** in SuiteSparse), `ldoor`
  (n=952,203, nnz(LU)=319M, structural), `dielFilterV3real` (n=1,102,824,
  nnz(LU)=1.14B, electromagnetics). 4 of 6 are SuiteSparse; the LU/U
  **factors themselves are generated by running the paper's own 3D
  numerical LU factorization** (with METIS nested-dissection ordering) on
  each base matrix — i.e. this is the one surveyed paper using a *genuine*
  numerically-factorized triangular system with real fill-in, not a
  structural stand-in (contrast with all 4 other papers below).
- **timing protocol**: `nrhs=1`. `SuperLUStat_t.utime[SOLVE]` isolates the
  SpTRSV wall time from `utime[FACT]` (symbolic+numeric LU factorization);
  the paper states factorization dominates end-to-end run time ("10s to
  3000s... most of the time is spent in symbolic and numeric LU
  factorization before calling SpTRSV") — SpTRSV time is a small,
  separately-instrumented fraction. No explicit repeated-solve loop was
  found in the drivers read (`pddrive3d.c`, `pddrive3d1.c`); `pddrive3d1.c`
  exists specifically to reuse one factorization across **multiple**
  `PDGSSVX3D` solve calls with different RHS ("we factorize A only once...
  and reuse... in the subsequent call"), i.e. the amortization pattern
  exists in the codebase but no reps-count for the SC'23 figures was
  confirmed from the extracted text — flagged as an open question.
- **timing scope**: solve-phase only (`utime[SOLVE]`), plus separately
  reported inter-grid/intra-grid communication and FP-op breakdown (Fig. 5,
  6, 9 in the paper — "time breakdown averaged over all MPI ranks").
  Analysis/ordering (METIS ND) and numeric factorization are one-shot,
  reported separately, and dominate wall time but are explicitly excluded
  from the plotted SpTRSV numbers.
- **precision & correctness**: fp64 (`pd*` driver prefix = parallel double).
  A component-wise backward error `berr` is computed per RHS by
  `pdgssvx3d`, but **no explicit pass/fail numeric threshold was found in
  the driver code** — `berr` is printed, not gated. (`matCheck()` in
  `pddrive3d1.c` is an unrelated internal consistency check between two
  copies of the redistributed matrix, not a solve-accuracy check.)
- **metric**: wall time (seconds); speedup vs. the paper's own "baseline 3D
  SpTRSV" [Sao et al.] and vs. a communication-optimized 2D SpTRSV
  baseline. No GFLOP/s reported (consistent with the field: SpTRSV's low
  arithmetic intensity makes wall time / strong-scaling the customary
  metric, not throughput).
- **baselines**: baseline (non-optimized) 3D CA-SpTRSV algorithm; 2D
  communication-optimized SpTRSV. Machines: Cori Haswell (CPU, up to 2048
  cores), Crusher (AMD MI250X), Perlmutter (NVIDIA A100, up to 256 GPUs).
  Claims: up to 3.45x vs. baseline 3D (CPU), 6.5x GPU-3D vs. CPU-3D, scales
  to 256 GPUs vs. 4 GPUs for the existing 2D algorithm.
- source: `gh api` listing of `EXAMPLE/{pddrive3d.c,pddrive3d1.c}`,
  `SRC/double/pdgstrs.c` (located via GitHub code search); paper PDF at
  liuyangzhuan.github.io/docs/3DSpTRSV_SC23.pdf, fetched and text-extracted
  with `pypdf` (WebFetch could not render this PDF directly) — Table 1,
  Section 4 (Numerical Results), and Appendix A.2 (Artifact
  Description/Reproducibility) read in full.

## 2. Zarebavani, Cheshmi, ... Dehnavi — HDagg: Hybrid Aggregation of
   Loop-carried Dependence Iterations in Sparse Matrix Computations
   (IPDPS'22)

- key: `conf/ipps/ZarebavaniCLSD22`, artifact:
  github.com/BehroozZare/HDagg-benchmark
- **workloads**: driven by `scripts/SpTrSv_Final.sh` — an SBATCH loop over
  `matrix/*.mtx` (no explicit filter/count visible in the script itself;
  matrix set populated separately, not enumerated in the repo). README
  usage example: `./build/demo/HDAGG_SpTRSV input/apache2.mtx 10`
  (SuiteSparse matrix `apache2`, 10 threads).
- **timing protocol** (code-verified, `demo/SpTRSV_runtime.h` classes all
  extend `FusionDemo` — the same base class used by
  sparse-specialize/partially-strided-codelet, both being
  Sympiler-ecosystem artifacts from the same research group):
  `FusionDemo::evaluate()` calls `build_set()` (scheduling/level-set
  construction) **once**, timed into `analysis_time_`, then runs
  `fused_code()` (the actual solve) `num_test_` times (**default 5**,
  no override found in the SpTRSV driver), takes the **median** via
  `sym_lib::time_median`. No separate warmup pass before the 5 timed runs.
- **timing scope**: solve-only for the median statistic; analysis/level-set
  time reported separately via `analysisTime()`. `SpTrSv_Final.sh` sets
  `OMP_NUM_THREADS=20`/`MKL_NUM_THREADS=20` on a 40-core-per-node
  allocation (Cascade Lake), i.e. CPU-only, MKL used as a baseline
  implementation (`SpTRSVMKL` class referenced alongside HDagg's own
  scheduler variants in the same driver family).
- **precision & correctness**: fp64 (`FusionDemo` members are all
  `double`). `FusionDemo::testing()` checks `is_equal(0, m_, correct_x_,
  x_, 1e-6)` — combined abs/rel tolerance 1e-6 — only if a `correct_x_`
  reference was supplied to the constructor.
- **metric**: not directly visible in the fetched header (CSV output via
  `PRINT_CSV` macros elsewhere in the Sympiler framework); paper claims (per
  abstract) 3.56x over MKL on SpTRSV/ILU/IC kernels combined.
- **baselines**: Intel MKL SpTRSV, plus HDagg's own predecessor scheduling
  algorithms (levelset, LBC — Locality-Based-Coarsening) evaluated in the
  same driver family (`Sptrsv_LL_Serial`, `SpTrsv_LL_Wavefront`, etc. all
  visible as sibling classes in `SpTRSV_runtime.h`).
- source: `scripts/SpTrSv_Final.sh`, `demo/SpTRSV_runtime.h` (class
  hierarchy), `demo/SpTRSV_runtime.cpp` (driver `main`), and (for the
  shared harness) `sparse-specialize/partially-strided-codelet`'s
  `demo/FusionDemo.h`/`FusionDemo.cpp`, which HDagg's own repo does not
  duplicate but structurally matches exactly (`num_test_=5`, median,
  `analysis_time_` field, `is_equal` correctness check with the same
  signature) — cross-confirmed as the shared harness rather than assumed.

## 3. Cheshmi, Cetinic, Dehnavi — Vectorizing Sparse Matrix Computations
   with Partially-Strided Codelets (SC'22)

- key: `conf/sc/CheshmiCD22`, artifact:
  github.com/sparse-specialize/partially-strided-codelet
- **workloads**: `demo/SPTRSV_demo.cpp` takes one `.mtx` file per run
  (`sym_lib::read_mtx(config.matrixPath)`); no bundled matrix list —
  matrices supplied externally (same "any Matrix-Market file" pattern as
  HDagg). If the input matrix is non-symmetric (`stype<0`) it is
  METIS-reordered and made "full", then **the lower-triangular part `L1_ord`
  is taken directly from the (possibly reordered) input matrix `A` itself**
  — no factorization step of any kind. This is a structural-extraction
  protocol, not a solve of a real LU/Cholesky factor.
- **timing protocol** (code-verified, `FusionDemo::evaluate()`, same class
  as HDagg above): `num_test_=5` (default, unchanged in `SPTRSV_demo.cpp`),
  median of 5 timed `fused_code()` calls per variant, `build_set()` (the
  codelet-mining/scheduling step) timed once into `analysis_time_` and
  reported as a **separate CSV column** ("Sympiler Inspector Time", "DDT
  Inspector Time", "MKL Inspector Time" — the demo prints inspector/analysis
  time for every competing method side by side in the same CSV row).
- **timing scope**: solve-only for the timed median; up to 9 competing
  SpTRSV variants benchmarked in the same run (`SpTRSV Base`, `Vec1`,
  `Vec2`, level-set `Vec`/`NoVec`, `Parallel LBC`, `Parallel Vec2 LBC`,
  Supernodal Sympiler, MKL serial/parallel, the paper's own DDT
  serial/parallel) — all sharing one correctness reference (`sol_sptrsv`
  from the `Baseline` serial run).
- **precision & correctness**: fp64 (`double *sol`, `FusionDemo` members).
  Same `is_equal(..., 1e-6)` check inherited from `FusionDemo::testing()`
  as HDagg.
- **metric**: per-variant wall time (`elapsed_time`), reported in a single
  CSV row with matrix name, dimension, nnz, thread count, tuning params.
  No GFLOP/s column found for SpTRSV specifically (unlike the SPMM demo in
  the same repo, which does compute FLOPs).
  Paper claims 1.67x/4.1x/[X]x over MKL for SpMV/SpMM/SpTRSV respectively
  per the track abstract (the SpTRSV number was truncated in the abstract
  text available).
- **baselines**: MKL (serial + parallel `SpTRSVMKL`), multiple
  level-set/LBC-scheduled variants, the paper's own DDT codelet-generated
  code. Hardware not confirmed from the fetched files (no cluster/CPU model
  string found in the demo source).
- source: `demo/SPTRSV_demo.cpp` (driver), `demo/FusionDemo.h`/
  `FusionDemo.cpp` (shared timing harness), `README.md` (build/run usage).

## 4. Ahmad, Yilmaz, Unat — A Split Execution Model for SpTRSV (TPDS'21)

- key: `journals/tpds/AhmadYU21`, artifact:
  github.com/ParCoreLab/Split_SpTRSV
- **workloads**: matrices auto-downloaded from SuiteSparse by matrix ID via
  the bundled `libUFget` library (`./silu_test matrix_id mode`), or supplied
  as a local `.mtx` file. README worked example: matrix "FullChip" (UF ID
  2380). No fixed matrix list found in the repo (download-on-demand
  design); paper evaluates on two CPU-GPU machines (Xeon Gold 6148 + V100;
  Core i7-8700K + GTX1080 Ti) per the README's citation of the paper.
- **workload derivation — important**: `src/main.cpp` calls
  `silu_test.Factorize(&matrix, &L, &U, "dummy")`, and
  `include/dummyFactorize.h` (`// Dummy ILU0 Factorization`) makes clear
  this is **not** a real incomplete-LU factorization despite the name — it
  literally partitions the nonzeros of the *original* input matrix `A` into
  `L` (entries with `col<row`) and `U` (entries with `col>row`) and assigns
  each a **fresh random value** (`rand()%10+1`), discarding `A`'s own
  numeric values entirely. The code's own comment says as much: "we are
  only interested in the sparsity pattern, not values." This is the same
  structural-extraction protocol as papers #3 and #5, just with randomized
  rather than reused values.
- **timing protocol** (code-verified, `src/main.cpp`): `ITERATIONS=10`
  outer loop; **each of the 10 iterations re-runs the full pipeline**
  (dummy factorize -> `Analyze()` [scheduling/split-point selection] ->
  `trsv()` [solve]) and accumulates `sptrsv1_time_new` etc. into running
  sums that are divided by `ITERATIONS` at the end. There is **no warmup**
  and **no separation of a one-time analysis cost from the 10 repeated
  measurements** — analysis (`levels_time_new`, `dag_analysis_time_new`,
  `split_time_new`, `data_structures_time_new`, `algo_analysis_time_new`,
  summed into `total_analysis`) is re-measured and re-averaged every
  iteration alongside the solve, which is a genuine methodological gap:
  the framework's own selling point (find-split-point-once, reuse it) is
  not reflected in how its own benchmark driver amortizes cost.
- **timing scope**: `std::chrono` (`using namespace std::chrono` in
  `main.cpp`) for host-side phases; separate H2D/D2H timers
  (`h2d_sptrsv1_time_new`, `d2h_spmv_time_new`, etc., `float`-typed,
  consistent with `cudaEventElapsedTime`) bracket data movement for the
  split CPU/GPU execution modes, reported as distinct CSV columns (not
  folded into the solve number).
  Analysis and communication are both reported as line items, per-mode
  (CPU-only / GPU-only / CPU-GPU-split, 6 policy cases switched on in the
  driver).
- **precision & correctness**: fp64 (`val_type` = `double` by default in
  `common.h`). `silu_test.ValidateResult(y, x_ref, matrix.n, 1)` is called
  every iteration; the reference `x_ref` is generated via
  `SerRef(..., RANDOM_REF, ...)` (random reference vector, forward-multiply
  to get `b`, same generate-known-solution pattern as paper #5). Exact
  tolerance used by `ValidateResult` was not confirmed (not in the files
  fetched) — open question.
- **metric**: per-mode wall time (ms, "All times in milli-seconds" per the
  driver's own printout), written to `results_for_revision_{hybrid,ELMC,
  MKL}.txt`. No GFLOP/s. Paper claims up to 10x speedup from splitting.
- **baselines**: ELMC (row/column-wise GPU SpTRSV), MKL SpTRSV (CPU),
  Sync-Free, SLFC, cuSPARSE v2, ELMR — supported per README, HTS evaluated
  separately (external harness, not integrated into the main driver).
- source: `src/main.cpp` (driver, iteration/timing loop),
  `include/dummyFactorize.h` (workload-derivation code), `include/
  common.h` (`val_type`), `README.md` (build/run/matrix-source usage).

## 5. Zhang, Su, Liu, He, Wu, Du, Wang — YuenyeungSpTRSV: A Thread-Level
   and Warp-Level Fusion Synchronization-Free Sparse Triangular Solve
   (TPDS'21)

- key: `journals/tpds/ZhangSLHWDW21`, artifact:
  github.com/JiyaSu/YuenyeungSpTRSV
- **workloads**: README states "we evaluate YuenyeungSpTRSV with 245
  matrices from the Florida Sparse Matrix Collection [= SuiteSparse] on
  four GPU platforms" — no explicit nnz/size filter recovered from the
  repo itself (the 245-matrix list is not checked into the repo; only a
  `matrix/` folder placeholder and a single CLI usage example,
  `./YYSpTRSV example.mtx`).
- **workload derivation**: `CUDA/main.cu` reads an arbitrary matrix `A` via
  `read_mtx`, then `change2tran(...)` extracts "the unit-lower triangular
  sparsity structure of input Matrix A" into `L` — i.e. the same
  structural-extraction protocol as papers #3 and #4 (take `A`'s own lower
  triangle, don't factorize). `csrValL_tmp` values come from `A` itself
  (not randomized, unlike Split_SpTRSV), and the diagonal is implicitly
  unit (see kernel: `x_i = (b_i - sum) / d_csrVal[rowend-1]`, i.e. it does
  divide by the stored last nonzero of the row rather than assuming exactly
  1, so "unit-lower-triangular" in the comment is a slight misnomer — the
  actual diagonal entry used is whatever nonzero already sits there).
- **timing protocol** (code-verified, `CUDA/YYSpTRSV.h`,
  `common.h`): `BENCH_REPEAT=100` (compile-time macro, `#ifndef`-guarded,
  overridable at build time but not overridden by the checked-in
  `Makefile`). **Both** the level/warp-partition preprocessing step
  (`matrix_warp(...)`) and the solve kernel are each run `BENCH_REPEAT`
  times in their own loop and averaged (`time_cuda_pre /= BENCH_REPEAT`,
  `time_cuda_solve /= BENCH_REPEAT`) — i.e. **mean**, not median, and no
  explicit warmup iterations before the averaged loop (the first of the
  100 timed launches serves as the de facto "warmup" and is included in
  the average, unlike TileSpMV/DCS-SpMV in the SpMV track's separate
  200-warmup convention).
- **timing scope**: preprocessing (`pre_time`) and solve (`solve_time`)
  are cleanly separated into two different averaged numbers, both printed.
  Timer: `gettimeofday` (wall clock, millisecond resolution via
  `tv_sec`/`tv_usec` arithmetic), wrapping `cudaDeviceSynchronize()` calls
  — no CUDA-event-based device timer used, unusual for a GPU-kernel paper
  in this era (contrast with the SpMV track's mostly-CUDA-event convention)
  and a source of host-side jitter in the reported numbers. Each solve
  iteration re-zeroes `d_get_value`/`d_x`/`d_id_extractor` via `cudaMemset`
  before timing starts (correct — avoids a false "already solved" fast
  path across iterations), but the `cudaMemcpy` of `x` back to host happens
  **inside** the timed loop (`cudaMemcpy(x, d_x, ...)` is the last
  statement before `gettimeofday(&t2, ...)`), so **D2H transfer of the
  solution vector is included in the reported solve time**, which most
  GPU-kernel papers (and the SpMV survey's convention) explicitly exclude.
- **precision & correctness**: `VALUE_TYPE` configurable (double by
  default per `common.h` seen: `#ifndef VALUE_TYPE #define VALUE_TYPE
  double`), README explicitly calls out single/double as a build-time
  choice. Correctness: `main.cu` checks `abs(x_ref[i]-x[i]) > 0.01*
  abs(x_ref[i])` — **1% relative tolerance**, the loosest of all 5 surveyed
  papers, and notably risky for a *synchronization-free* algorithm whose
  entire premise is spin-waiting on a flag array with no barrier — race
  outcomes can legitimately vary run-to-run, and a loose one-shot 1%
  check on a single random `b` does not protect against an
  occasionally-wrong answer the way a tighter tolerance + repeated
  correctness re-checks across iterations would. `x_ref`/`b` generated via
  `get_x_b` (same generate-a-known-solution-and-forward-multiply pattern
  as paper #4).
- **metric**: `GFLOPS = 2*nnzL/(1e6*time_ms)`, plus a bandwidth figure
  (`dataSize/(1e6*time_ms)` GB/s) using a CSR-array byte-accounting
  formula essentially identical in structure to the SpMV track's DCS-SpMV
  formula. Abstract claims 7.14 GFLOPS/s average, 5.98x over the prior
  synchronization-free SpTRSV, 4.83x over cuSPARSE SpTRSV.
- **baselines**: prior synchronization-free SpTRSV algorithms (warp-per-row
  design), cuSPARSE SpTRSV. Hardware: GTX 1080, Tesla V100, RTX 2080 Ti
  (CUDA); Radeon Vega 11 APU (OpenCL, separate code path, not surveyed in
  depth here).
- source: `CUDA/main.cu` (driver), `CUDA/YYSpTRSV.h` (kernel + timing +
  metric code, read in full), `CUDA/common.h` (macros), `README.md`.

## Divergences

**1. How the "triangular factor" is obtained from a SuiteSparse matrix —
the single biggest methodological split in this track, and one none of the
5 abstracts mention.** Four of five surveyed artifacts (#2 HDagg's SpTrSv
path, #3 partially-strided-codelet, #4 Split_SpTRSV, #5 YuenyeungSpTRSV) do
**not** factorize anything: they take an arbitrary SuiteSparse matrix `A`
and mechanically extract its lower- (or upper-) triangular nonzero pattern,
optionally replacing the values (randomized in #4, kept as-is in #3/#5,
unconfirmed for #2), and call the result "L". Only the SC'23 paper (#1)
solves the output of a *real* sparse LU factorization with genuine fill-in
and supernodal blocking. These two protocols produce triangular systems
with **structurally different DAG shapes** (a real LU factor's elimination
tree has far more fill-in-driven parallelism/height variation than an
arbitrary matrix's raw lower triangle), so a "4.83x over cuSPARSE" claim
under protocol A is not measuring the same thing as a "3.45x over baseline"
claim under protocol B — cross-paper speedup numbers in this track are
not comparable without knowing which protocol produced the input. The spec
below fixes this by naming ONE canonical extraction method for the
single-node/single-GPU variants (matching the 4/5 majority — cheap,
reproducible without a factorization-library dependency) and reserving
genuine-LU-factor inputs for the distributed variant, where SC'23 is the
only real precedent anyway.

**2. Repeated-solve / amortization count**: BENCH_REPEAT=100 mean (#5),
num_test_=5 median (#2, #3, shared Sympiler harness), ITERATIONS=10 running
mean that **re-does the analysis phase every iteration** rather than
amortizing it (#4 — a real bug relative to the paper's own thesis), and no
confirmed in-code repeat loop at all for the SC'23 figures (#1, single run
per configuration due to LU-factorization cost dominating wall time). No
two papers use the same count or the same statistic (mean vs. median).

**3. Analysis/level-set-construction vs. solve — universal split, divergent
granularity.** All 5 papers separate "figure out the DAG/schedule/split
point once" from "run the solve." But the granularity differs sharply:
YuenyeungSpTRSV reports one number (`pre_time`); Split_SpTRSV reports five
sub-phase timers (`levels`, `dag_analysis`, `split`, `data_structures`,
`algo_analysis`) but then re-measures all five every iteration (see
divergence #2); the Sympiler family (#2, #3) times the whole analysis step
as one `analysis_time_` field but separates it cleanly from the 5 solve
timings; SC'23 folds ordering+factorization into one large `utime[FACT]`
that is orders of magnitude bigger than `utime[SOLVE]` and isn't
"level-set construction" as an isolated concept at all (parallelism comes
from the elimination tree computed as a byproduct of numeric
factorization, not a separate scheduling pass over a given triangular
matrix).

**4. Correctness tolerance**: 1e-6 abs+rel (Sympiler family, #2/#3, the
tightest), unconfirmed/not-found-in-fetched-code (#4), 1% relative (#5, the
loosest — and arguably too loose given #5's synchronization-free
correctness risk noted above), and no explicit numeric threshold at all in
the driver code (#1 — `berr` computed but not gated pass/fail before the
timing numbers are reported, violating the "correctness gate before timing
counts" fairness principle outright).

**5. Timer**: `gettimeofday` (#5, and includes D2H-in-timed-region, a real
flaw), `std::chrono` + presumed CUDA-event-based H2D/D2H sub-timers (#4),
a Sympiler-framework `timing_measurement` class of unconfirmed
implementation shared by #2/#3, and SuperLU_DIST's internal
`SuperLU_timer_()` (#1, standard library convention, MPI_Wtime-based,
not independently re-verified from the fetched files).

**6. Metric**: GFLOP/s + GB/s (#5), per-variant wall time only (#2, #3,
#4), wall time + strong-scaling speedup curves (#1, no throughput metric
at all — consistent with the field's general preference for time/speedup
over GFLOP/s given SpTRSV's low, matrix-structure-dependent arithmetic
intensity).

**7. Scale/scope**: #1 is the only distributed-memory (multi-node,
multi-GPU, MPI) paper in the track; #2-#5 are all single-node
(CPU-multicore or single-GPU). This is a legitimate different claim, not
just a methodology gap — it gets its own variant below rather than being
forced into the same input/protocol as the single-device papers.
