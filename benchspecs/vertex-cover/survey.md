## conf/ipps/YamoutBJMH22 — Parallel Vertex Cover Algorithms on GPUs

- **Problem scope**: two formulations, both via GPU-parallel branch-and-bound
  search-tree traversal: **MVC** (Minimum Vertex Cover — find the smallest
  vertex cover) and **PVC** (Parameterized Vertex Cover — find a cover of
  size <= parameter k, or determine none exists). Both are exact/exhaustive
  search-tree algorithms (not heuristics), so correctness has a hard
  ground-truth answer per instance, not an approximation ratio.
- **Hardware/toolchain**: CUDA + C/C++; repo's `test/runGraphs.py` driver
  submits runs via SLURM (`srun --partition=cmps-ai --nodes=1
  --ntasks-per-node=1 --cpus-per-task=1 --nodelist=onode11`) — i.e. runs
  are pinned to a single named node for reproducibility, single task
  (single GPU) per run.
- **Workloads/inputs** (from `test/test_graphs/` directory listing, 20
  named instances, and `test/runGraphs.py`'s `MVCS` dict which hard-codes
  the KNOWN OPTIMAL vertex-cover size for each): a deliberately mixed
  suite spanning:
  - DIMACS clique-benchmark "hat" family (adversarial, hard search-tree
    instances): `cop_hat300-{1,2,3}`, `cop_hat500-{1,2,3}`,
    `cop_hat700-{1,2}`, `cop_hat1000-{1,2}`
  - real-world networks: `CAIDA` (Internet AS topology), `Sister-Cities`,
    `lastfm-asia` (social network), `Power-Grid`, two Wikipedia hyperlink
    graphs (`formated_wikipedia_link_csb`, `formated_wikipedia_link_lo`),
    `formated_movielens-100k_rating`, two protein-interaction networks
    (`formated_maayan-vidal`, `formated_maayan-figeys`)
  - PACE-challenge-style exact instances: `vc-exact_009`, `vc-exact_023`
  All ship as edge-list `.txt` files in `data/GraphDatabase/` (with a
  README "Graph Database Links.txt" tracing original sources) and a
  filtered `test/test_graphs/` subset actually driven by the test harness.
- **Timing protocol** (from `test/runGraphs.py`): grid search over
  `ROOT_DEPTH=[16]` and `BLOCK_DIM in {64,128,256,512,1024}`; for each
  (graph, version, MVC/PVC-instance, depth, block-dim) combination, the
  binary is run **`REPEAT=3`** times via separate SLURM job submissions,
  each writing a row to `src/Results/Results.csv`. No explicit discarded
  "warmup" run is coded — all 3 repeats are recorded as data rows (the
  spec below treats the first of the 3 as an implicit warmup per this
  project's convention, since GPU JIT/context-init effects on the first
  call are a known confound the paper's own script does not control for).
- **Precision & correctness**: exact integer search — the `MVCS` dict in
  the test driver hard-codes the KNOWN OPTIMAL MVC size per graph (ground
  truth from external exact solvers), so **correctness = returned cover
  size exactly equals the known optimum** for MVC, or **existence/size
  <= k is correctly decided** for PVC (`-k` flag computed as
  `k_offset + MVCS[filename]`, i.e. PVC instances are generated by adding
  a small offset to the known-optimal size, testing both "yes, k is
  achievable" and near-threshold "no" cases depending on the offset sign).
  This is an EXACT problem — no approximation ratio applies; the
  correctness gate is binary (right optimal size or wrong).
- **Metric**: wall time per run (Results.csv row), and (from
  `USE_COUNTERS=1` build target) auxiliary per-SM work-distribution
  counters (`NODES_PER_SM`) and per-phase time breakdown (`Counters`) —
  i.e. the paper also studies load-imbalance across streaming
  multiprocessors, not just aggregate time, though the counters build is
  explicitly noted in the README as "won't run efficiently" (a
  profiling-only, non-benchmark build mode).
- **Baselines**: the README does not name an external baseline directly,
  but the paper's own abstract/README frames the contribution as
  addressing GPU-specific challenges (narrow binary search tree limiting
  sub-tree-level parallelism; two structures compared: "local-stack" vs.
  "global-worklist", per this track's `one_liner` field in
  `benchmark_groups.json`) — i.e. the paper's own two algorithm variants
  (local-stack, global-worklist) are compared against each other as much
  as against prior work; a companion/derivative repo
  (`HusseinAmro/component-aware-vertex-cover-gpu`, "Faster Vertex Cover
  Algorithms on GPUs with Component-Aware Parallel Branching", also
  arXiv-indexed at 2512.18334) exists as a later, related work building on
  this baseline, useful as an external comparison point if available at
  benchmark-build time.

## Divergences

Single-paper track: no cross-paper divergence. One internal tension worth
flagging: the paper's own test driver treats all 3 repeats as equally
valid data rows (no explicit warmup discard), which understates run-to-run
GPU-launch-overhead variance for the SHORT-running instances in the mixed
suite (some `cop_hat300-*` instances likely finish in milliseconds, where
first-call CUDA context/JIT overhead could dominate) — this spec adds an
explicit warmup convention the paper's own script does not have.
